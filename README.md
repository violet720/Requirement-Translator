
# Requirement Translator
### 需求轉譯與澄清輔助工具

> From Ambiguous Requests to Clear Requirements.
>
> 從模糊需求出發，建立更清晰的需求共識。

**核心設計原則：Clarify Before Implementing.**

先理解使用者真正的需求，再評估適當的資訊技術解決方案。

---

## 01. Project Overview｜專案概述

Requirement Translator 是一項以需求工程（Requirements Engineering）為核心的系統雛型，旨在協助專案經理（Project Manager, PM）、系統分析師（System Analyst, SA）及工程師釐清需求描述中的模糊資訊，降低不同角色之間的理解落差。

本專案目前以規則式文字分析（Rule-based Text Analysis）為主要方法，透過需求辨識、澄清問題、人工補充與規格整理，探索如何將原始需求轉換為更明確、可供討論及技術評估的需求資訊。

本系統定位為需求分析輔助工具，而非取代客戶、PM 或工程師進行專業判斷。

## 02. Problem Statement｜問題定義

資訊系統開發不僅涉及程式設計，也需要整合不同利害關係人的需求與期待。

當需求缺乏明確定義或確認機制時，可能造成規格認知落差、反覆溝通、重工、專案延遲及交付成果不符合客戶期待等問題。

本專案主要關注以下三項問題。

### P-01｜需求描述缺乏明確性

客戶可能以「操作方便」、「系統快速」、「資料安全」等主觀描述提出需求，卻未提供具體的使用情境或衡量標準。

因此，PM 與工程師可能對同一項需求產生不同理解。

### P-02｜潛在需求與限制條件未被充分辨識

客戶提出的需求可能未完整涵蓋業務規則、資料權限、既有系統限制或例外情況。

若缺乏進一步確認，可能使後續系統設計與實際業務需求產生落差。

### P-03｜需求缺乏完整的確認機制

即使需求已經過初步討論，若缺少完整性檢查、利害關係人確認及未解決事項紀錄，仍可能在開發過程中產生規格爭議。

## 03. Proposed Solutions｜問題與解決方案

本專案提出三項對應的解決策略。

### S-01｜模糊需求辨識與澄清

**對應問題：P-01**

透過規則式文字分析，辨識需求中的特定模糊描述，並根據辨識結果產生澄清問題。

範例：

- 原始需求：希望系統速度快。
- 待釐清資訊：缺乏具體效能標準。
- 澄清問題：希望哪些操作更快？可接受的回應時間為多少？

**預期價值：** 協助 PM 將主觀描述整理為更具體的需求資訊。

**目前狀態：** 已有初步雛型功能。

### S-02｜潛在需求與限制探索

**對應問題：P-02**

規劃透過結構化檢查項目，提醒 PM 從使用者情境、業務流程、資料權限、例外情況及技術限制等面向進一步確認需求。

範例：

- 原始需求：跨分公司查閱資料需要主管核准。
- 待確認事項：誰具有核准權限？
- 延伸問題：授權範圍、有效期限及撤銷條件為何？

**預期價值：** 降低重要條件未經討論而被遺漏的風險。

**目前狀態：** 規劃擴充中。

### S-03｜需求完整性檢查與人工確認

**對應問題：P-03**

規劃建立需求檢查清單及人工確認流程，協助 PM、客戶與工程師辨識未解決事項。

預計包含：

- 未確認需求標示
- 已確認條件紀錄
- 業務需求確認
- 技術可行性評估狀態
- 需求變更與確認紀錄

**預期價值：** 提高需求資訊的可追溯性，降低過早進入開發的風險。

**目前狀態：** 規劃中。

## 04. Project Objectives｜專案目標

### O-01｜提高需求描述的明確性

協助使用者辨識模糊描述，透過澄清問題補充必要資訊。

對應：P-01、S-01。

### O-02｜改善潛在需求與限制的辨識

協助 PM 探索原始需求中可能未被提出的業務規則、使用情境與限制條件。

對應：P-02、S-02。

### O-03｜建立可追蹤的需求確認流程

探索完整性檢查、人工確認與需求狀態紀錄機制。

對應：P-03、S-03。

## 05. Stakeholder Analysis｜利害關係人分析

| 角色 | 主要需求 | 關注重點 |
|---|---|---|
| Client 客戶 | 表達業務需求 | 功能符合實際需要 |
| PM 專案經理 | 整理需求與協調溝通 | 範圍、進度與風險 |
| SA 系統分析師 | 分析與規格化需求 | 完整性、一致性與可追溯性 |
| Engineer 工程師 | 評估及實作系統 | 技術可行性、限制與驗收標準 |

各角色可能對同一項需求具有不同關注面向，因此需求確認應包含必要的跨角色溝通。

## 06. Requirements Analysis｜需求分析

以下區分目前雛型能力與後續規劃需求。

### 6.1 Functional Requirements｜功能需求

| 編號 | 功能需求 | 狀態 |
|---|---|---|
| FR-01 | 輸入並分析原始需求 | 初步實作 |
| FR-02 | 辨識特定模糊詞彙 | 初步實作 |
| FR-03 | 產生需求澄清問題 | 初步實作 |
| FR-04 | 呈現 PM 與工程師的需求視角 | 初步實作 |
| FR-05 | 整理 User Story 與 Acceptance Criteria | 初步實作 |
| FR-06 | 探索潛在限制與業務規則 | 規劃擴充 |
| FR-07 | 提供需求風險辨識與排序建議 | 規劃中 |
| FR-08 | 檢查需求完整性及未解決事項 | 規劃中 |
| FR-09 | 提供人工確認與狀態紀錄 | 規劃中 |

註：初步實作代表目前雛型已有相關功能邏輯，並不表示功能已通過完整驗證。

### 6.2 Non-functional Requirements｜非功能需求

以下為後續需要評估的品質要求：

**NFR-01｜Usability 可用性**

介面應提供易於理解的需求輸入與分析流程。

**NFR-02｜Maintainability 可維護性**

需求辨識規則與介面邏輯應具備可維護性，以利後續擴充。

**NFR-03｜Privacy 隱私保護**

應評估使用者輸入需求中可能包含的個人資料與企業機密，並設計適當的資料處理方式。

**NFR-04｜Reliability 可靠性**

系統應清楚標示分析限制，避免將未經確認的需求誤判為已完成驗證。

上述非功能需求尚需進一步建立可衡量的驗收標準。

## 07. System Design｜系統設計

### 7.1 Conceptual Workflow｜概念流程

1. 使用者輸入原始需求。
2. 系統執行規則式文字分析。
3. 系統辨識特定模糊描述。
4. 系統產生澄清問題。
5. 使用者補充相關資訊。
6. 系統整理需求描述與驗收條件。
7. 後續規劃加入人工確認及狀態追蹤。

### 7.2 Design Principles｜設計原則

**DP-01｜Clarify Before Implementing**

需求尚未釐清前，不直接假設特定技術解決方案。

**DP-02｜Human-in-the-Loop**

系統提供分析建議，但需求最終確認仍由相關利害關係人負責。

**DP-03｜Traceability**

需求、澄清問題、確認結果與後續規格應建立可追溯關係。

**DP-04｜Transparency**

清楚揭露規則式分析的限制，不將系統輸出視為必然正確。

## 08. Implementation｜技術實作

### 8.1 Current Approach｜現有方法

目前雛型主要使用瀏覽器端 JavaScript 與預先設定的文字判斷規則處理需求輸入。

系統會依辨識結果產生相應的分析內容及澄清問題。

### 8.2 Technical Limitations｜技術限制

- 無法完整理解所有自然語言語意。
- 可能無法正確辨識複雜、隱含或跨領域需求。
- 需求信心程度不等同於需求正確性。
- 系統產生的驗收條件仍需人工審查。
- 尚未建立完整的需求驗證與追溯機制。

## 09. Testing & Validation｜測試與驗證

目前尚未建立完整的系統性測試結果。

後續預計從以下面向進行驗證：

| 測試面向 | 驗證內容 |
|---|---|
| TC-01 | 能否辨識預先定義的模糊需求 |
| TC-02 | 澄清問題是否對應原始需求 |
| TC-03 | 多重需求是否能合理處理 |
| TC-04 | 人工補充後是否仍有未確認事項 |
| TC-05 | 產生的驗收條件是否具備可測試性 |

測試結果將另行紀錄，不預先宣稱系統已有效降低專案延遲或溝通成本。

## 10. Limitations & Future Roadmap｜限制與未來規劃

### Phase 1｜Current Prototype

建立基本的需求辨識、澄清問題與規格整理流程。

### Phase 2｜Requirements Enhancement

擴充需求限制探索、完整性檢查與人工確認機制。

### Phase 3｜Risk & Traceability

探索需求風險辨識、優先排序與需求追溯功能。

### Phase 4｜AI-assisted Analysis

評估整合生成式 AI 的可行性，並研究如何降低錯誤推論與不適當的需求假設。

上述為規劃方向，尚不代表既定開發承諾。

## 11. Reflection｜專案反思

本專案從「為什麼 PM 與工程師對同一項需求產生不同理解？」出發，逐步探索需求模糊、潛在限制與需求確認機制的重要性。

透過專案設計，嘗試將組織協調與需求分析的觀點轉化為資訊工具，並進一步思考技術實作與管理決策之間的關係。

本專案仍處於持續學習及改進階段，後續將透過測試、需求驗證與文件化提升其完整性。
